## 4. 阶段分组和完成口径

### 4.1 基础骨架：阶段0～8

目标是一次性建立最终模块结构、最终磁盘格式、完整 IndexBackend 边界、最终 RuntimeControl 并发骨架，以及可独立测试的目录、索引和 VLog 底层能力。

骨架阶段不得使用以后需要替换的临时格式、简化指针、单 Keyspace 适配、直接 Fjall 调用或临时单线程状态机。后续阶段只能填充既定模块和协议，不得为接入新功能而重建基础架构。

### 4.2 60分基础功能：阶段9～14

目标是使用最终骨架完成：

- `Db::open` 和 Drop；
- Put、Get、Delete；
- WriteBatch；
- `sync=false`；
- `sync=true` 和空同步屏障；
- 真实 Stats 内存快照；
- 正常重开和崩溃恢复；
- 单线程公共 API 端到端验证。

60分阶段仍使用最终 WriteGate、RuntimeControl、提交和恢复结构，但不要求完成公共 Db 的多线程集成矩阵。Snapshot、Iterator、Range和DestroyDB在该里程碑明确返回结构化 `Unsupported`。

60分完成不等于完整 P0，不得宣称系统设计全部验收通过。

### 4.3 60分之后的P0：阶段15～19

目标是补齐：

- Snapshot、Iterator和Range；
- 完整生命周期、Descriptor cleanup和DestroyDB；
- 全部错误状态机、重试和故障注入矩阵；
- 多线程并发正确性和历史检查；
- LevelDB 1.23 Conformance；
- Rust 1.90 MSRV；
- Linux L4 OS崩溃/掉电专项验收。

只有阶段15～19全部验收后，才能声明完整 P0 完成。

## 7. 构建、测试和回归门禁

每个阶段至少执行：

```bash
cargo build --locked
cargo test --locked
```

规则：

1. 修改过程中先运行本阶段定向测试；
2. 阶段完成后运行全量 `cargo test --locked`；
3. 全量测试必须包含两个Fjall spike、当前阶段测试和此前所有阶段测试；
4. 只有命令退出码为0且测试结果为0 failed，阶段才可能验收；
5. 禁止删除测试、降低断言、添加 `#[ignore]`、吞掉错误或重建损坏目录来取得绿色结果；
6. 失败时先记录命令、错误、根因和修复，再重新运行定向测试及全量构建测试；
7. 无法在规范内修复时标记 `阻塞`，不得继续下一阶段。

## 8. 独立Git提交门禁

每个已验收阶段必须对应一个独立 Git 提交。禁止把两个阶段混入同一提交，也禁止在阶段尚未验收时提前提交为完成状态。

提交前必须确认：

```bash
git status --short
git diff -- <本阶段允许修改的全部文件>
cargo build --locked
cargo test --locked
```

提交门禁：

1. `git diff`只能包含本阶段【实现文件】列出的文件；
2. 不得覆盖、回滚或夹带用户在阶段开始前已有的改动；
3. `cargo build --locked`退出码必须为0；
4. `cargo test --locked`必须全量通过；
5. 两个Fjall spike必须继续通过；
6. 必须核对不存在被忽略、删除或弱化的测试；
7. 提交信息使用统一格式：

   ```text
   stage <N>: <阶段名称>
   ```

8. 提交成功后，在状态表“验收提交”列记录完整或可唯一解析的commit hash；
9. 阶段最终输出必须包含commit hash；
10. 若工作树中存在无法与本阶段隔离的用户改动，停止提交并报告，不得擅自暂存、回滚或合并这些改动。

独立提交的目的，是在后续发生回归时能够准确定位首次破坏契约的阶段。提交本身不能替代测试证据。

## 9. 统一阶段输出

每个阶段完成时必须输出：

1. 改动文件清单；
2. 关键实现说明，并对应设计文档章节；
3. 定向测试命令与结果；
4. `cargo build --locked`命令、退出码和结果；
5. `cargo test --locked`命令、退出码、通过/失败数量；
6. 本阶段验收Git提交hash；
7. 未完成项、阻塞项或经用户批准的偏差；
8. 是否允许进入下一阶段的明确结论。

不得只输出“测试通过”“实现完成”等无法核验的结论。
