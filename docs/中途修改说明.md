## 2026-08-24：阶段7按受信任环境假设暂缓原子 no-follow 改造

- 所属阶段：`01_基础骨架阶段`的阶段7“目录、根锁与初始化”。
- 发现的问题：当前对 `LOCK`、`FORMAT`、`FORMAT.tmp`、`index/`、`vlog/` 和 VLog 数据文件的静态符号链接检查会拒绝链接，但“检查路径”与“使用路径”仍是两次独立操作；若有外部主体在其间替换受管对象，存在 TOCTOU 窗口，因此 no-follow 语义并非原子。
- 用户批准：当前假设数据库目录处于受信任环境，不存在人为或其他外部进程并发替换文件或目录的情况，因此本阶段不修复该原子性缺口。
- 信任边界：Fjall 内部后台操作是上述并发假设的唯一例外；阶段7 Open 准备路径仍必须在首次身份校验和只读Recovery分析完成前以零后台线程打开 Fjall，不允许 Fjall 在只读检查期间改动受管状态。
- 影响边界：该授权不放宽静态布局校验；受管子项如果在检查时已是符号链接，仍必须 fail-closed，不得跟随。
- 后续要求：如果威胁模型扩大到不受信任的目录或并发管理工具，需将受管子项改为相对根目录句柄的 `openat`/`fstatat`/`renameat`/`unlinkat` 或等价原子 no-follow 实现，不再分离检查与使用。

## 2026-08-24：阶段7延迟 Fjall 后台线程启动

- 所属阶段：`01_基础骨架阶段`的阶段7“目录、根锁与初始化”。
- 发现的问题：阶段7 Open 准备路径原先调用普通 `FjallBackend::create/open_existing`；Fjall 3.1.8 会在 `Database::open()` 内立即启动 Flush/Compaction worker，使后台任务可能早于 `DatabaseIdentity`、HeadSeq、DurableFrontier 和恢复前置状态的完整校验。
- 设计要求：系统设计文档第4.7.1节和第8.1节要求，首次身份验证和只读Recovery分析完成前不得启动Fjall后台维护；正常Writer、descriptor cleanup、其他RustKV后台维护和公共读写仍必须等待Recovery全部完成。
- 实际修复：保留普通 `create/open_existing` 的原有 worker 语义，另增阶段7专用 `create_for_open_preparation/open_existing_for_open_preparation`；专用入口通过 Fjall 3.1.8 的 `worker_threads_unchecked(0)` 以0 worker 打开或创建后端。新建、打开既有数据库和校验中断初始化三条阶段7路径均改用专用入口。
- 验证结果：测试会确认成功初始化、既有库重开和中断初始化校验所得后端均为零 worker 准备态；初始化 SyncAll 三元组在该模式下仍能持久化并跨进程崩溃恢复。
- 后续边界：阶段7返回的 `OpenPreparation` 故意不运行 Fjall worker；后续阶段只能在完成首次身份验证和只读Recovery分析后关闭该Backend，再以正常worker重开同一索引、二次验证身份并执行Recovery。该准备态不得执行Recovery写入，也不得被当成完整 `Db` 实例。

## 2026-08-25：阶段8验收时确认的内部调用契约与延期项

- 所属阶段：`01_基础骨架阶段`的阶段8“VLog真实文件层”最终验收。
- `FrontierSync` 调用契约：`sync_through` 成功返回的 token 必须由后续提交协调器最终且恰好一次传给 `frontier_succeeded` 或 `frontier_failed`；调用方不得直接丢弃 token。当前 `FrontierSync::Drop` 不会自动解除 `pending_sync_id`，丢弃 token 会使同一 Writer 后续追加和同步持续返回 Busy。用户确认后续调用方会遵守该线性消费契约，因此本阶段不增加 Drop 自动失败处理。
- `PreparedEnvelope` 信任边界：Writer 只接收由已验收的 `prepare_envelope` 产生且未被 crate 内部调用方篡改的 `PreparedEnvelope`。调用方不得修改 `commit_seq`、`vlog_begin`、`vlog_end`、`PhysicalChunk.position` 或 `PhysicalChunk.bytes` 等关键字段。Writer 保留必要的位置、结构和事务末端校验，但不将不受信任的人工构造或篡改对象作为本阶段能力边界。
- `create_new` 冲突分类：惰性创建 VLog 文件使用排他创建，因此遇到已存在目标文件时不会覆盖或截断数据；当前该冲突会被归类为普通 `Io + FixEnvironmentAndReopen`，而非更精确的物理布局错误。这保留 fail-closed 功能语义，但错误诊断精度暂不修复。
- VLog 同步错误分类：文件或目录同步失败时，Writer 会保留 dirty/pending 状态并停止后续写入，不会误报持久化成功。当前对 `sync_file`/`sync_directory` 的 `EINTR/EAGAIN` 等瞬态错误不做独立的有界重试或资源耗尽分类，而是保守返回 `Io + FixEnvironmentAndReopen`。该延期项影响异常时的可用性与诊断精度，不改变正常路径的磁盘字节或持久化真值。
- Reader 与 FileSet 的已知延期项：Reader `metadata/fstat` 的瞬态错误处理、`EAGAIN/ENFILE` 精确退避预算仍按本文档前两项记录执行，不视为已实现。FileSet 缓存命中路径会先读取 catalog identity，存在一次额外的短临界区；这是性能与并发竞争优化项，不影响缓存容量、文件身份或读回正确性，本阶段不修改。
- 验收影响：上述边界不改变阶段8正常单页、跨页、跨文件写入和读回，不改变布局、CRC、Pointer、dirty/Frontier 成功语义或 Writer 唯一能力。它们是后续集成必须遵守的内部契约或已批准的异常可用性/性能延期项，不得在后续阶段被默认忘记。

## 2026-08-30：暂缓阶段15 User Index不可信长度的分配前校验

- 所属阶段：`03_60分后P0功能阶段`的阶段15“Snapshot、Iterator和Range”。
- 发现的问题：Fjall User Index的Get和Iterator适配目前会按磁盘返回的长度先分配并复制Value或Key/Value，之后才由ValuePointer解码或VLog Key交叉校验发现非法长度；尚未在分配前校验User Key为`1..=60000`字节、EncodedValuePointer精确为16字节。
- 用户批准：本次不修改Fjall读取适配层，将该P1记录为已知实现安全边界，后续专项修复。
- 影响边界：正常16字节Pointer和合法User Key的Snapshot/Get/Iterator/Range功能不受影响；持久化User Index中的异常超大Key或Pointer可能触发过量分配，分配失败时还可能被误报为保持`Healthy`的`ResourceExhausted`，而非持久损坏应有的`Corruption + Poisoned`。
- 后续要求：为User Index增加与Internal Index分离的受限转换路径，在任何拥有型复制前校验Key和Pointer长度；非法长度必须返回`Corruption`并通过现有读错误映射将活实例升级为`Poisoned`，不得用扩大公共API或暴露Fjall类型的方式修复。

## 2026-08-30：阶段16 Destroy部分删除重入优先的可信环境取舍

- 所属阶段：`03_60分后P0功能阶段`的阶段16“完整生命周期、Descriptor cleanup和DestroyDB”。
- 保留的语义：Destroy严格按VLog、`vlog/`、`index/`、FORMAT.tmp、FORMAT的顺序删除。当合法FORMAT仍存在但`vlog/`已缺失时，实现将该形态视为先前一次Destroy已经进入部分删除阶段，允许继续删除剩余`index/`；不再要求该剩余index能完整打开或完成DatabaseIdentity校验。
- 选择理由：递归删除Fjall index可能在任意内部目录项后中断；FORMAT最后删除的前提下，`vlog/`缺失是按规范删除顺序已经开始破坏性操作的重入证据。保留该推断可使修复环境后的重试继续收敛，而不会因index已部分删除而永久卡住。
- 信任边界：该取舍仅适用于受信任的本地嵌入式环境，假设受管目录形态只由RustKV/Fjall和按协议重试改变。它不防御人为拼接FORMAT与其他数据库index、手工删除`vlog/`后替换index、错误的部分备份恢复，或其他违反受管目录所有权的外部修改；这些场景可能导致Destroy删除无法再通过Identity证明归属的剩余index。

## 2026-09-03：Open Recovery启用Fjall worker以解除反压

- 所属范围：系统设计文档第4.7.1节、第8.1节、第8.8节及阶段12～14的Open/Recovery组装。
- 发现的问题：原Open时序让0-worker Fjall Backend同时承担只读Recovery分析和Recovery写入。大量`sync=false`写入留下至少4个sealed memtable或L0积压时，Recovery的普通Fjall `WriteBatch::commit()`会进入`local_backpressure()`；0-worker无法执行Flush/Compaction，等待不会自行解除。
- 用户批准：最小调整“Recovery完成前Fjall后台Flush/Compaction尚未启动”的旧约束。FORMAT、首次DatabaseIdentity、固定Keyspace布局和只读Recovery分析完成前仍严格禁止启动Fjall worker；分析成功后允许启动Fjall内部Flush/Compaction支持Recovery写入。公共Db、正常Writer、Descriptor cleanup和其他RustKV后台维护仍必须等Recovery全部成功后才开放或启动。
- 固定时序：根锁贯穿全程；零worker打开并完成首次身份验证与只读分析；生成完全拥有型RecoveryPlan；关闭零worker Backend；正常worker重开同一索引；立即再次验证DatabaseIdentity；使用该Backend执行全部Recovery commit；Recovery成功后同一Backend直接进入运行期，不进行第三次重开。
- 失败边界：首次身份验证或只读分析失败时不得创建worker-enabled Backend；第二次打开、第二次身份验证或Recovery失败时不得返回半可用Db；任何失败均不启动Descriptor cleanup。
- 不变协议：不改变D/H、DurableFrontier、RecoveryState、Undo、Trim、DatabaseIdentity、公共API、错误分类或Benchmark语义；不跳过Fjall反压，也不增加Benchmark后置sync或sleep。
