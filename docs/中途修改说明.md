## 2026-08-21：暂缓阶段3的VLog CRC单次遍历改造

- 所属阶段：`01_基础骨架阶段`的阶段3“VLog物理格式与布局算法”。
- 发现的问题：`prepare_envelope`当前先遍历操作计算Envelope CRC，随后再次遍历并编码物理记录、计算Record CRC；对于Put操作会重复读取Key和Value内容，尚未满足系统设计文档第6.1.5节要求的“在编码并写入记录的同一次数据遍历中增量计算记录CRC和Envelope CRC”。
- 用户批准：本阶段暂不修改该编码路径，先记录此项偏差，留待后续接入真实VLog Writer时处理。
- 后续要求：布局阶段只读取长度并预先确定Footer位置及`vlog_end`；实际编码和写入阶段必须在唯一一次Key/Value内容遍历中同时更新Record CRC与Envelope CRC，不得为Envelope CRC再次读取Value。
- 影响边界：当前磁盘字节格式、CRC计算结果和功能测试不受影响；该记录只推迟内部遍历方式的整改，不授权改变任何Magic、字段、长度、CRC覆盖范围或持久化语义。

## 2026-08-24：阶段7按受信任环境假设暂缓原子 no-follow 改造

- 所属阶段：`01_基础骨架阶段`的阶段7“目录、根锁与初始化”。
- 发现的问题：当前对 `LOCK`、`FORMAT`、`FORMAT.tmp`、`index/`、`vlog/` 和 VLog 数据文件的静态符号链接检查会拒绝链接，但“检查路径”与“使用路径”仍是两次独立操作；若有外部主体在其间替换受管对象，存在 TOCTOU 窗口，因此 no-follow 语义并非原子。
- 用户批准：当前假设数据库目录处于受信任环境，不存在人为或其他外部进程并发替换文件或目录的情况，因此本阶段不修复该原子性缺口。
- 信任边界：Fjall 内部后台操作是上述并发假设的唯一例外；阶段7 Open 准备路径仍必须在身份校验与恢复完成前以零后台线程打开 Fjall，不允许 Fjall 在检查期间改动受管状态。
- 影响边界：该授权不放宽静态布局校验；受管子项如果在检查时已是符号链接，仍必须 fail-closed，不得跟随。
- 后续要求：如果威胁模型扩大到不受信任的目录或并发管理工具，需将受管子项改为相对根目录句柄的 `openat`/`fstatat`/`renameat`/`unlinkat` 或等价原子 no-follow 实现，不再分离检查与使用。

## 2026-08-24：阶段7延迟 Fjall 后台线程启动

- 所属阶段：`01_基础骨架阶段`的阶段7“目录、根锁与初始化”。
- 发现的问题：阶段7 Open 准备路径原先调用普通 `FjallBackend::create/open_existing`；Fjall 3.1.8 会在 `Database::open()` 内立即启动 Flush/Compaction worker，使后台任务可能早于 `DatabaseIdentity`、HeadSeq、DurableFrontier 和恢复前置状态的完整校验。
- 设计要求：系统设计文档第4.7.1节和第8.1节要求，Writer、descriptor cleanup、Fjall 后台维护和公共读写不得在 Open 第7步完成前启动；阶段7本身更明确禁止开放任何后台任务。
- 实际修复：保留普通 `create/open_existing` 的原有 worker 语义，另增阶段7专用 `create_for_open_preparation/open_existing_for_open_preparation`；专用入口通过 Fjall 3.1.8 的 `worker_threads_unchecked(0)` 以0 worker 打开或创建后端。新建、打开既有数据库和校验中断初始化三条阶段7路径均改用专用入口。
- 验证结果：测试会确认成功初始化、既有库重开和中断初始化校验所得后端均为零 worker 准备态；初始化 SyncAll 三元组在该模式下仍能持久化并跨进程崩溃恢复。
- 后续边界：阶段7返回的 `OpenPreparation` 故意不运行 Fjall worker；后续阶段只能在完成设计文档规定的恢复、物理尾校验和运行时组装后，通过明确的重开或激活步骤启动后台能力，不得把当前准备态误当成已启动后台任务的完整 `Db` 实例。

## 2026-08-25：暂缓阶段8 Reader 元数据瞬态错误处理

- 所属阶段：`01_基础骨架阶段`的阶段8“VLog真实文件层”。
- 发现的问题：`ValueLogReader::read_pointer` 对目标文件执行 `metadata/fstat` 时，当前没有为 `EINTR/EAGAIN` 执行设计规定的有限重试；该调用失败后还会统一映射为普通 `Io + FixEnvironmentAndReopen`，与同一读取路径其他瞬态资源错误使用的 `ResourceExhausted + RetrySameInstance` 语义不一致。
- 用户批准：本阶段本次修改暂不修复该分支，只记录偏差；Writer 写入重试、FileSet 打开重试和位置读重试的现有预算不因此放宽或改变。
- 影响边界：正常 `metadata/fstat` 成功、真实非瞬态 I/O 失败以及 Pointer/Record 损坏校验不受影响；罕见的 `metadata/fstat` 瞬态失败目前可能被误报为需要修复环境并重开实例的普通 I/O 错误。
- 后续要求：为目标文件元数据读取增加可注入且有界的瞬态重试边界，并补充 `EINTR/EAGAIN` 成功边界、预算耗尽、错误种类和重试建议测试；不得把真实 I/O 错误或数据损坏改报为资源耗尽。

## 2026-08-25：暂缓阶段8 EAGAIN/ENFILE 精确退避预算

- 所属阶段：`01_基础骨架阶段`的阶段8“VLog真实文件层”。
- 发现的问题：Writer 位置写、FileSet 打开和位置读对 `EAGAIN` 已实施最多3次的有界重试，但尚未执行设计文档第4.6.5节规定的 `1ms/2ms/4ms` 退避；FileSet 打开遇到 `ENFILE` 时当前还与 `EAGAIN` 共用3次立即重试预算，而设计要求退避10ms后只重试1次。
- 用户批准：本次不修改该重试调度，只记录偏差；该偏差不改变正常文件 I/O 的磁盘字节、追加位置、CRC、dirty/Frontier 或读回结果，预算耗尽后仍返回结构化资源错误且不存在无限重试。
- 影响边界：资源瞬态耗尽时的重试次数和时间节奏与冻结设计不一致，可能影响故障期间的延迟和成功概率；现有 `ENFILE` 测试固定的是当前3次预算，不能视为精确设计预算已经验收。
- 后续要求：引入测试可注入的 sleeper/退避器，将 `EAGAIN` 改为3次 `1ms/2ms/4ms` 退避，将 `ENFILE` 改为10ms后单次重试，并分别覆盖成功边界、预算耗尽、调用次数和退避序列；不得使用依赖真实墙钟抖动的脆弱测试。

## 2026-08-25：阶段8验收时确认的内部调用契约与延期项

- 所属阶段：`01_基础骨架阶段`的阶段8“VLog真实文件层”最终验收。
- `FrontierSync` 调用契约：`sync_through` 成功返回的 token 必须由后续提交协调器最终且恰好一次传给 `frontier_succeeded` 或 `frontier_failed`；调用方不得直接丢弃 token。当前 `FrontierSync::Drop` 不会自动解除 `pending_sync_id`，丢弃 token 会使同一 Writer 后续追加和同步持续返回 Busy。用户确认后续调用方会遵守该线性消费契约，因此本阶段不增加 Drop 自动失败处理。
- `PreparedEnvelope` 信任边界：Writer 只接收由已验收的 `prepare_envelope` 产生且未被 crate 内部调用方篡改的 `PreparedEnvelope`。调用方不得修改 `commit_seq`、`vlog_begin`、`vlog_end`、`PhysicalChunk.position` 或 `PhysicalChunk.bytes` 等关键字段。Writer 保留必要的位置、结构和事务末端校验，但不将不受信任的人工构造或篡改对象作为本阶段能力边界。
- `create_new` 冲突分类：惰性创建 VLog 文件使用排他创建，因此遇到已存在目标文件时不会覆盖或截断数据；当前该冲突会被归类为普通 `Io + FixEnvironmentAndReopen`，而非更精确的物理布局错误。这保留 fail-closed 功能语义，但错误诊断精度暂不修复。
- VLog 同步错误分类：文件或目录同步失败时，Writer 会保留 dirty/pending 状态并停止后续写入，不会误报持久化成功。当前对 `sync_file`/`sync_directory` 的 `EINTR/EAGAIN` 等瞬态错误不做独立的有界重试或资源耗尽分类，而是保守返回 `Io + FixEnvironmentAndReopen`。该延期项影响异常时的可用性与诊断精度，不改变正常路径的磁盘字节或持久化真值。
- Reader 与 FileSet 的已知延期项：Reader `metadata/fstat` 的瞬态错误处理、`EAGAIN/ENFILE` 精确退避预算仍按本文档前两项记录执行，不视为已实现。FileSet 缓存命中路径会先读取 catalog identity，存在一次额外的短临界区；这是性能与并发竞争优化项，不影响缓存容量、文件身份或读回正确性，本阶段不修改。
- 验收影响：上述边界不改变阶段8正常单页、跨页、跨文件写入和读回，不改变布局、CRC、Pointer、dirty/Frontier 成功语义或 Writer 唯一能力。它们是后续集成必须遵守的内部契约或已批准的异常可用性/性能延期项，不得在后续阶段被默认忘记。

## 2026-08-26：暂时接受 Fjall OwnedWriteBatch 的延后分配边界

- 所属阶段：`02_60分基础功能阶段`的阶段9“提交预检、事务规划和Descriptor构造”。
- 发现的问题：阶段9会在 VLog 追加前完整构造并使用 fallible allocation 预留 `IndexAtomicBatch`，但现有 Fjall 3.1.8 适配层只能在 `commit_atomic` 中调用 `OwnedWriteBatch::with_capacity`；Fjall 内部使用不返回分配错误的 `Vec::with_capacity`，因此真实后端 Batch 的该次分配仍会发生在 VLog 追加之后。
- 用户批准：当前以内存充足时 Put、Delete 和 WriteBatch 的正常功能正确为验收目标；暂时接受该问题仅留在内存耗尽等异常路径，本阶段不扩展 IndexBackend/Fjall 能力边界。
- 影响边界：正常内存条件下，`IndexAtomicBatch` 的 User mutation、Transaction Descriptor 和 HeadSeq 内容不受影响；若 Fjall `OwnedWriteBatch` 的容量分配在 VLog 已追加后耗尽内存，进程可能终止，而不是返回可分类的 `ResourceExhausted + NotCommitted`。恢复必须仍将未被 Fjall 已提交状态引用的完整或残缺 Envelope 视为未提交后缀，不得发布其 User Index 状态。
- 后续要求：如需完全满足系统设计第7.1.2节的异常分配契约，需要在不向公共 API 暴露 Fjall 类型的前提下，为 IndexBackend 增加可在首个 VLog 字节前完成真实后端 Batch 容量准备的内部能力，并增加对应故障注入验证。
